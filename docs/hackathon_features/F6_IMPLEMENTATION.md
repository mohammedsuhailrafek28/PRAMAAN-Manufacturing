# F6 — Reduced federated recall: implementation, runbook, evidence and limits

Branch `feature/hackathon-federated-recall`, from `manufacturing-demo-v1.1` (`cf180a0`). Synthetic data; **no network, no sockets** (file-based bulletin). Design: `F6_FEDERATED_RECALL_DESIGN.md`. Raw evidence: `f6_evidence/`.

> **Read first.** All keys are generated by a local `keygen` on one machine. A valid signature shows a message is intact and was made with the pinned key. It is **not independent company authentication**, not independent custody, and says nothing about physical bearing identity. Not production-ready.

## 1. What was built (and what was not)

| Requirement | Implementation |
|---|---|
| 1. One synthetic supplier signs and publishes a recall alert | `federation/supplier.py::Supplier.issue_alert` writes a signed `ALERT` to `bulletin/alert-NNNNNN.json` (sequence-numbered, hash-chained, expiring) |
| 2. Two separate factory instances verify signature and freshness/replay | `federation/node.py::FactoryNode.receive` for factory A and B (own directory, ledger, registry, checkpoint, federation store, key): authenticate → closed schema → window → addressed → strict sequence + `prevHash` chain → store. **The ledger is never opened.** |
| 3. Each factory resolves the supplier-qualified lot with its own registry | `federation/lotmap.py` → unchanged `LotRegistry.resolve` (+ supplier id equality). A maps `NSB-204`→`BR-204`; B (different registry) maps the same label →`BR-771`. Anything else is `LOT_UNMAPPED` |
| 4. Operator adoption is mandatory before the local recall announcement | `FactoryNode.adopt(alert, operator, confirm)`: named operator + typed first-12-hex of the alert hash; the stored envelope is **re-authenticated** (the store is unprotected); then the existing `Manufacturing.announce`. No other code path writes a ledger |
| 5. Independent evaluation with unchanged evaluator + FORMAT_V3 | `respond` calls the unchanged `snapshot(trusted_anchor=…)`; counts exist only if `ANCHORED_CURRENT`. The checkpoint cycle is the existing `checkpoint_ops.propose/accept` |
| 6. Only scoped counts | `RESPONSE` has a closed schema: status, `heldMotors`, `heldByEvidenceFinding{AFFECTED,UNRESOLVED,EXCLUDED_WITH_EVIDENCE}` (frozen evaluator values), `heldOnlyByIdentityGuard`, checkpoint checksum. No serials, lots, customers, events, ledgers, paths |
| 7. Supplier-side view of the two results | `Supplier.board(...)` verifies each response and renders a terminal table and a static `board.html`, one row per factory |

**Not built, by instruction:** corrections, retraction, WIDEN, any new UI, a server/HTTP route, central copy of ledgers. Only `ALERT` is accepted by factories (a signed `CORRECTION` or `RESPONSE` is rejected as `UNSUPPORTED_TYPE`).

## 2. Safety design
* Imported messages can: be recorded; after an operator, announce the existing local recall (adds holds). They cannot clear a hold, authorize shipment, edit the registry, or change evaluator/FORMAT_V3/guard. `node.py` calls only `Manufacturing.announce`, `snapshot` and `close` (tested by static scan); the federation package has no socket/HTTP imports and `server.py` does not mention it.
* One immutable recall scope per database is **unchanged**: a second *mapped* lot is refused by the existing rule (`ADOPTION_REFUSED`), first policy unchanged (tested).
* `respond` reports counts only if the ledger actually holds the adopted scope: a forged adoption row in the unprotected federation store yields `ADOPTION_REFUSED`, no counts (tested).
* A zero/absent count is **not a clearance**; the board says so.

## 3. Messages (`PRAMAAN-FED/1`)
Envelope `{format, kid, body, signature}`; Ed25519 over `b"PRAMAAN-FED/1\0" + JCS(body)`; pinned trust file per node (`PRAMAAN-FED-TRUST/1`, roles `supplier`/`factory`). Ed25519 is `cryptography` 50.0.1 (cffi 2.1.1, pycparser 3.12) from the **feature-isolated, sha256-pinned** `ci/requirements-f6-federation.lock` (same pins as F5); the frozen `ci/requirements-windows.lock` is untouched. No custom primitives. JCS uses the project's existing `rfc8785`.
ALERT: `alertId, issuer, seq, prevHash, iat, exp (≤7 days, 60 s skew), lot{supplierId,part,supplierLot}, affectedSlots, humanText, recipients?`. Rejection reasons are distinct and recorded: `WRONG_KEY, BAD_SIGNATURE, UNKNOWN_SENDER, WRONG_SENDER_ROLE, UNSUPPORTED_TYPE, MALFORMED_BODY, INVALID_EXPIRY, EXPIRED, NOT_YET_VALID, NOT_ADDRESSED, REPLAY, STALE_SEQUENCE, OUT_OF_ORDER, PREVHASH_MISMATCH, DUPLICATE_ALERT_ID`.

## 4. Run it
```
python -m venv v && v/Scripts/python -m pip install --require-hashes -r ci/requirements-windows.lock -r ci/requirements-f6-federation.lock
v/Scripts/python -B research/federated_recall/demo_f6.py WORKDIR     # WORKDIR new/empty; ~20 s; transcript in f6_evidence/demo_transcript.txt
v/Scripts/python -B -m unittest application.test_federation -v      # 34 tests
```
Demo storyline (≈4 min): limits banner → S signs one alert → three attacks rejected at A (attacker key, edited text, attacker signature under S's key id) → real alert accepted at A and B, **ledgers untouched** (policy count 0, state identical) → replay and expired alert rejected → same label `NSB-204` maps to `BR-204` at A and `BR-771` at B → wrong confirmation refused, operators adopt → responses while stale carry **no counts** → existing checkpoint cycle → A holds 2 (2 AFFECTED), B holds 2 (1 AFFECTED + 1 held only by the identity guard) → S's board → a second alert for unmappable `NSB-999` is `LOT_UNMAPPED`, never "not affected". The checkpoint acknowledgements are **scripted** in the demo; in real use a person decides.
Fallback ladder: (1) live demo; (2) show `f6_evidence/demo_transcript.txt` and the generated `board.html`; (3) the tests and mutation results are the proof if no live run is possible.

* **Interoperability** (`research/federated_recall/interop_check.py`): 16 envelopes (3 valid, 13 tampered/forged/wrong-role/wrong-type/expired/extra-field) verified by the reference (`cryptography`), a Node/OpenSSL verifier and a PyNaCl/libsodium verifier, each with its own canonical JSON: all agree (`f6_evidence/interop.json`). The first run exposed a gap in the *independent* verifiers (nested response `counts` fields were not checked); they were extended and the case kept. Scope limit: chains, lot mapping, adoption and ledger behaviour are not independently re-implemented.
* **Gates:** full local A–K in a clean LF clone of `8e6c3a3`: `PASSED` (`f6_evidence/gates_summary.json`); engine/foundation/integration trees unmodified; manifest delta 15 added, 0 modified (`docs/CI_INVENTORY_CHANGE_F6.md`). Local only — no hosted-CI result is claimed.

## 6. Findings worth knowing
1. **The existing guard is stricter than the design assumed.** A look-alike of a lot in use elsewhere on the same factory (e.g. `BR-77I` beside `BR-771`), or a look-alike recorded as the installed lot, makes the existing `checkpoint_ops.accept` **refuse** ("acknowledgement cannot override this"). That factory's response stays `PENDING_CHECKPOINT` with no counts until its own people resolve it through the existing flows. This is safe (no wrong count) but means one dirty ledger silences its factory. The clean "unresolved" demo uses an unrelated unverified sighting (`QX-77`), which scoped containment holds; it appears as `EXCLUDED_WITH_EVIDENCE` held *only by the identity guard*, which the response states explicitly rather than hiding.
2. **Strict chain trade-off.** A factory accepts only `seq == last+1` with the right `prevHash`. An alert that never reached a factory (lost, or rejected as expired) leaves a gap; all later alerts are then `OUT_OF_ORDER` at that factory until redelivered or the supplier restarts a new chain. There is no resync protocol in this build.

## 7. Limitations (not hidden)
* Local demo keys; no rotation, revocation or key discovery; same-host custody; not independent authentication or verification; H1/H2 independent validation is not claimed.
* The federation store is outside H1/H2 and the checkpoint; a local attacker can edit it. Mitigations: adoption re-authenticates the stored envelope; counts require the ledger to hold the adopted scope; replay state (`hwm`) can however be rolled back by such an attacker.
* Counts are factory-asserted; the supplier cannot verify them. The `heldOnlyByIdentityGuard` field and the response timing reveal that an identity problem exists at a factory (metadata).
* File transport only: "publishing" is writing a file; delivery is outside the code. No message confidentiality.
* Lot mapping ignores registry effective dates (`at=None`) and trusts the locally authored synthetic registry; the supplier id used by the demo supplier is a fixed registry value.
* One adopted recall per database, hence one alert per factory ledger; a second mapped lot is refused. No correction/retraction/WIDEN.
* No UI changes and no screenshots; supplier view is a terminal table plus a static page.
* The demo's checkpoint acknowledgements are scripted; operator confirmation is a typed hash, not authentication.
