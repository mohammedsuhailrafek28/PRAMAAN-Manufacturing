# Digital Product Passport + QR Explorer (Option B)

Status: implementation for owner review. Not merged, not deployed. Synthetic data only. Loopback only (127.0.0.1).

## What it is

A standalone, read-only page, `recall-ui/passport.html`, that shows a per-motor passport built from the existing
`GET /api/snapshot` response:

- Overview: identity as recorded, current DE/NDE components, recall context, and a list of what is not recorded or unverified.
- Components: DE/NDE slots, current claim and replacement history, with links to the evidence events.
- Evidence: each claim to its events, with event IDs, source claims, capture and chain hashes, and what hashes do and do not show.
- Timeline: chronological, filterable by category, with capture-session gaps called out.
- Recall context: read-only, gated (see below).
- QR label: route-only QR with a print button.

Routes: `passport.html#/passport/<MTR-id>[/<tab>[/<eventId>]]`. `?mode=preview` is an explicit opt-in that loads
`public/data/passport-preview.json`; preview never shows recall status and never counts as verified.

## Trust model

- The projection (`src/passport/projection.ts`) is pure. It imports only `domain/glossary` and `domain/types` (enforced by a test), makes no network or storage calls and does not mutate its input.
- Recall context is shown only when the existing, unmodified `verifyFreshness` accepts the snapshot. Otherwise the page says "Current recall status unavailable" and the records are labelled unverified. Regression detection withholds the passport.
- The decision is copied from the snapshot unchanged. The page never computes or upgrades a decision, and never presents a historical RELEASE_ELIGIBLE as current clearance.
- Supplier and raw-material data are always labelled unverified claims. Shipment is labelled "recorded, not an authorization".
- Customer, destination, shipment ID and operator/actor identifiers are omitted from the projection (tested with a forbidden-string list on all 7 units). This is UI omission, not API access control: `/api/snapshot` still carries them.
- Only `GET /api/snapshot` is used. A Playwright test asserts GET-only traffic and that journal sequence, head, decisions, notifications and event counts are unchanged after viewing every tab.
- No fixture fallback in live mode. A backend outage withdraws recall status and labels records stale.

## QR limits (stated in the UI as well)

- The QR encodes only `<origin>/passport.html#/passport/<unit id>`. It carries no customer, destination, source payload, hash, signature or verdict. Query and fragment of the current page are discarded (so `?mode=preview` never leaks into a QR).
- It is a link, not proof of authenticity and not anti-cloning: anyone can print the same QR on another motor.
- While the app is restricted to 127.0.0.1, scanning from another device will not work. Making it reachable is a deployment/security decision that is out of scope here.
- There is no access control on the page or on the API.

## Demo walkthrough (MTR-26004)

1. Start the app with the demo seeded and open `/passport.html#/passport/MTR-26004`.
2. Overview: capture coverage gap description, recall "Held under the recall policy", and the list of unrecorded items (no inspection, specification, certification, manufacturer identity; no trusted time source; capture gap for the Assembly station 2026-10-02 to 2026-10-09).
3. Components: DE currently BR-312 (serial BRG-MTR-26004-DE-R9, supplier claim Kaveri Precision). "Show replacement history" reveals the removed BR-204 bearing (Northstar Bearings claim), with install and removal records. NDE is BR-310.
4. Evidence: "View evidence for this claim" opens the event with IDs, source claims and hashes.
5. Timeline: 15 events in claimed order; filter by category; gap callout.
6. QR label: shows the route-only QR and print button, with the loopback and not-proof warnings.
7. Stop the backend: recall status is withdrawn ("unavailable"), records labelled stale, no fixtures are shown.

## Compatibility risks with Codex's branch

- `recall-ui/package.json` and `package-lock.json`: textual conflicts likely if Codex also changes dependencies.
- `vite.config.ts`: now multi-page; chunk layout changes (shared `styles-*.js` chunk).
- `playwright.config.ts`: unchanged, but the passport spec shares its webServer on port 4173 and starts isolated servers on 4185-4187.
- Freshness status strings and snapshot schema (see above).
- The H1/H2 snapshot latency growth (3 s at 50 entries) would also slow the passport page; the 4 s client timeout is shared.
- Existing Playwright runs rewrite tracked `docs/phase31-screenshots/*` and `docs/phase31-validation/browser-latency.json`; these were reverted and are not part of this change.
