# Phase 4A — multi-recall case management research

Date: 2026-10-21. Repository: `mohammedsuhailrafek28/PRAMAAN-Manufacturing`. Audited baseline: `phase3/unified-application`, **`4a9e8f2c11e5e12bfd6926bfb9f9a0ee0dd3fa57`**. Research branch: `research/phase4a-multi-recall`.

**Research recommendation: provisionally prefer A3, with explicit publication barriers and an append-only obligation history. Owner approval is required before design or implementation.** A1 is a credible constrained fallback; a union-policy A2 is unsuitable for the current kernel. The v3 *evaluation kernel* can plausibly remain unchanged for its currently supported policy shapes, but the existing lifecycle/persistence path is not a complete multi-recall or cross-revision lifecycle. Removing the application guard alone would be unsafe.

Only this report is changed. No schema, API, UI, migration, evaluator or feature was implemented. Claude's baseline audit and source branches/worktrees were not modified. No merge, deployment or MSME repository access occurred. References below point to code unchanged from the pinned baseline. “Confirmed” means inspected code or the disposable probes in §2; proposed behavior, estimates and acceptance tests are explicitly distinguished.

## 1. Current implementation audit — confirmed facts

### 1.1 Scope storage and the single-recall restriction

There is no recall-case table or case-scoped revision key. | The database does **not** enforce “exactly one row,” but `version` is globally unique: two cases each at revision 1 would conflict. No lifecycle state or authorization record exists. |
| [service.py:152](../application/service.py#L152) | `announce()` validates a lot; an identical affected-lot announcement returns the old policy; any different scope after an announcement is rejected. Closing, suspension, reopening, case ownership, revision activation, conflicting revision resolution and effective intervals are absent. These are new orchestration concepts, not existing v3 features waiting to be enabled.

### 1.2 Policies, coverage and evidence identity

- [ledger.py:273](../integration/pramaan_integration/ledger.py#L273) accepts an explicit policy with `policyId`, `recallId`, positive `version`, `announcedAt`, one `affectedPart`, a nonempty `affectedLots` list, DE/NDE `affectedSlots`, and either `CURRENT_INSTALLATION` or `HISTORICAL_OPERATION`. Historical operation requires a PASS protocol, qualification and inspection time bound not before announcement. The ledger can already evaluate different policy objects directly; application discovery/activation cannot.
- [policy.py:35](../recall-engine/pramaan_recall/policy.py#L35) matches a part and lot; [policy.py:257](../recall-engine/pramaan_recall/policy.py#L257) evaluates the scoped slots under one exposure basis. Combining several parts, or different rules for different lots/slots, is outside this policy shape.
- [ledger.py:69](../integration/pramaan_integration/ledger.py#L69) provisions sources, sessions and coverage in an immutable motor configuration. Mandatory capture, trusted-verifier sources, both slot bindings and conservative v3 attribution parameters are explicit. [ledger.py:107](../integration/pramaan_integration/ledger.py#L107) verifies the stored configuration hash. Updating coverage in place is unsupported and would violate existing triggers/hash checks.
- The engine's [coverageDigest](../recall-engine/pramaan_recall/engine.py#L164) is SHA-256 of `json.dumps(coverage, sort_keys=True)`; the ledger's [digest()](../integration/pramaan_integration/profile.py#L43) uses RFC 8785 canonical JSON for policy/configuration/manifest/bundle hashes. These are distinct digest schemes over distinct inputs: a policy digest is not a coverage digest or proof of a complete evidence snapshot. Preserve original bytes and algorithm identifiers; do not normalize/re-hash old records into a new scheme.
- Engine output includes policy ID/version, recall ID, semantics profile, engine version, coverage digest and watermark. A case's new policy revision must not silently replace any of those inputs for an old decision.

### 1.3 Decision persistence, identity and lifecycle

- [ledger.py:45](../integration/pramaan_integration/ledger.py#L45) defines append-only `motors`, `captures`, `events`, `rejections` and `decision_runs`. Events have globally unique IDs and `(motor, source, seq)` uniqueness. Decision runs have an ordinal primary key, `motor`, `policy_hash`, payload and payload hash; the `(motor, policy_hash, ordinal)` index is **not** a unique external decision-ID constraint. There is no foreign key from `policy_hash` to stored announcement policy bytes.
- [ledger.py:294](../integration/pramaan_integration/ledger.py#L294) loads history by `(motor, digest(entire policy))`. A changed policy version, scope or metadata hash starts a different history. It preserves old rows, but does not link a new policy's first decision to an old policy's standing decision.
- [lifecycle.py:28](../recall-engine/pramaan_recall/lifecycle.py#L28) uses only the last slash-separated policy-ID segment in `D-{case.caseId}-{suffix}-v{n}`. The ledger's [snapshot caseId](../integration/pramaan_integration/ledger.py#L254) is the motor serial, not a recall-case ID. Therefore two policies ending `/P1` for the same motor can generate identical displayed IDs, despite different policy digests and recall IDs. Within a fresh policy-digest stream numbering starts at v1.
- [lifecycle.py:13](../recall-engine/pramaan_recall/lifecycle.py#L13) compares only finding, action, review flag, reason codes, and each slot's reconciliation/current recorded lot. It excludes flags, evidence IDs, policy identity/version, coverage digest, detailed attribution/observations, obligations and other result details. On a matching signature, [line 34](../recall-engine/pramaan_recall/lifecycle.py#L34) returns the previous decision's fields with an updated watermark and `unchanged=True`; this does not prove all evidence or obligations are unchanged.
- [ledger.py:298](../integration/pramaan_integration/ledger.py#L298) retains requested horizons and recomputes their series; an identical stored payload is not inserted again. A new watermark can add an immutable run even when the engine reports no new decision version. Distinguish an evaluation receipt/run from a published decision version.
- Evidence supersession is handled by [engine.py:92](../recall-engine/pramaan_recall/engine.py#L92): visible corrections deactivate referenced events while retaining superseded evidence in the input/output. This is distinct from decision supersession, and neither implements cross-policy supersession.

### 1.4 Watermarks, replay and concurrency

- [watermark() / snapshot()](../integration/pramaan_integration/ledger.py#L229) require every configured motor-scoped source, including zero positions; validate contiguous prefixes and visible references; and return a manifest with configuration and evidence snapshot digests. Receipt position is not an assertion of event-time completeness. The kernel uses the selected producer sequence horizon, not a global time cutoff or shipment timestamp.
- [verified rows](../integration/pramaan_integration/ledger.py#L206) validates original capture bytes, native/wire equivalence, index identity and the motor hash chain. It checks the motor's stored rows before filtering to a historical watermark. Later corruption can therefore block historical replay; a persisted digest alone does not guarantee future availability of the required bytes.
- [Ledger.replay](../integration/pramaan_integration/ledger.py#L323) verifies the issued bundle/run, exact manifest and policy digest before calling engine replay. [engine replay](../recall-engine/pramaan_recall/replay.py#L12) selects the record's original semantics profile (legacy when absent) and checks coverage digest. It returns an evaluated finding/result, **not** a regeneration of all lifecycle IDs, supersession edges or communication state. Engine replay alone does not bind policy bytes; the ledger wrapper supplies that protection.
- [serialized_decision](../integration/pramaan_integration/ledger.py#L22) uses `BEGIN IMMEDIATE` for a single decision operation. The HTTP service's [process-local RLock](../application/server.py#L31) serializes its requests. Neither provides a durable multi-case generation/publication barrier. Captures have their own transactions; composite commands and per-motor fleet reads are not one transaction across every motor/case. Multi-process writers and policy activation require explicit coordination, not reliance on an RLock.

### 1.5 Global disposition, notifications and API assumptions

- There is **no persisted overall MotorDisposition**. [countDecisions](../recall-ui/src/domain/derive.ts#L21) counts one selected policy's decisions and skips missing ones; it is not “release across all recalls.” The [App](../recall-ui/src/App.tsx#L53) defaults/resets selection to the first supplied policy. Policy selection must not become a global-release control.
- [lifecycle.py:46](../recall-engine/pramaan_recall/lifecycle.py#L46) creates a precautionary hold and conditional obligation when a previous exclusion in the **same series** becomes non-excluded. `communicated` may be true/false/unknown; the application supplies no delivery evidence. A cross-policy revision has no `prev` and creates no such transition automatically.
- [service.py:263](../application/service.py#L263) builds notification display from **only the current decision's** obligation, labelled `NOT_SENT`. There is no independent obligation journal, recipient set, acknowledgement, retry or delivery record. Historical obligations can remain in old decision bundles yet disappear from the current notification list; see §2.
- [server.py:70](../application/server.py#L70) accepts `POST /api/recalls` with a lot but no recall-case/revision selector. Every resource GET builds the one-policy `snapshot()` first; `/decisions`, `/notifications` and lot investigation inherit its scope. A ledger block aborts that snapshot and returns 409 without fallback decisions. Missing/failed cases are not currently represented as explicit rows.
- [policy.py:184](../recall-engine/pramaan_recall/policy.py#L184) matches inspections by protocol, time bound, slot scope, qualification and result; it does not filter by top-level event `recallId`. Whether an inspection can satisfy two recalls is therefore a **new approval question**. Reusing a protocol ID across cases must not accidentally imply approved cross-case credit. A candidate boundary is globally distinct case/protocol identifiers with explicit revision mappings, rather than changing the kernel or silently filtering away evidence.

### Probe P2 — a current obligation is not a durable obligation journal

After seeding, `MTR-26005` stands at `D-MTR-26005-P1-v2`, `UNRESOLVED`, with reasons `UNTRUSTED_AFFECTED_OBSERVATION` and `PRIOR_EXCLUSION_WITHDRAWN`, `precautionaryHold=true`, and a conditional obligation referring to v1. Append one valid, unrelated `MATERIAL_ALLOCATED` claim through the existing synthetic MATERIAL source, then call `snapshot()` again.

Observed: `D-MTR-26005-P1-v3` remains `UNRESOLVED` and `RECALL_HOLD`, but has only `UNTRUSTED_AFFECTED_OBSERVATION`; `notificationObligation` and `precautionaryHold` are absent. The old obligation remains in immutable history, but the application's current-notification projection loses it. Source explanation: the withdrawal reason was appended after signature comparison, so the next plain result differs from the previous augmented signature and emits another version without recreating the original transition. **No false release was observed in this probe.** Independent obligation retention is still necessary for invariant 7, and signature handling needs explicit treatment for invariant 10. ## 3. Architecture alternatives

Definitions matter: A1 means separate case-owned evidence contexts/snapshots (potentially separate stores). A3 means one authoritative ledger and shared immutable snapshot references, with independent case evaluations and a distinct global publication layer. If A1 simply points at the same authoritative manifests and adds that publication layer, it converges toward A3 rather than remaining a different safety model.

| Criterion | A1 — independent evaluations and separate evidence contexts | A2 — combined policy evaluation | A3 — shared ledger, separate cases/decisions, explicit global disposition |
| --- | --- | --- | --- |
| Correctness | Per-case kernel fits. Safe only if every context contains complete motor/sibling/coverage evidence and all contexts have provable freshness; filtered lot-only histories are unsafe. A global gate is still required. | A naive union loses independent obligations, per-case reasons, dates and lifecycle. One engine call cannot express arbitrary parts, bases or inspection protocols. Conservative union can over-hold and still misassign conditions. | Fits kernel's one-policy model; explicit applicability and global barrier can prevent release on unknown/stale cases. Shared ledger does not automatically make orchestration correct. |
| Complexity | Lowest for two frozen research cases; evidence import, correction fan-out and multiple-store reconciliation grow quickly. | Small only for identical policies with unionable lots; general form requires a new policy algebra, evaluator semantics and proof. A wrapper that evaluates originals separately is aggregation, effectively A3/A1. | Moderate new case/revision registry, input identity, invalidation, publication and obligations. Avoids distributed evidence reconciliation. |
| Reproducibility | Good with archived complete input bytes/manifests per case; drift and duplicated provenance need detection. | Must archive the combination transformation, versions and mapping back to cases; ambiguous per-case replay is a serious blocker. | Strong with immutable policy/configuration/snapshot refs and versioned aggregation rule; historical global composition must also be stored. |
| Performance | Revalidates/copies common evidence per case; N contexts can multiply I/O/storage. Frozen copies offer isolation. | May save replay work only for genuinely identical semantics; distinct predicates still require work. Savings are hypothetical without a new supported kernel. | Allows shared validation at one pinned horizon; evaluation remains roughly proportional to applicable cases. Current ledger methods still repeat validation until a reviewed cache/context boundary exists. |
| Migration | Can preserve old database unchanged as one context; metadata mapping needed; cross-context identity/freshness unresolved. | Most disruptive: old individual decisions cannot be re-labelled as combined decisions without fresh evaluation. | Additive registry/envelope/journal can reference old bytes and scoped identities; not zero-risk (§7). |
| Hackathon feasibility | Credible frozen-snapshot fallback; not credible as live independent databases without a complete stale-state gate. | NO-GO for general multi-recall evolution under unchanged-kernel constraint. | Credible narrow synchronous prototype with full reevaluation, two cases and no optimized selective invalidation. Full lifecycle/operations exceed that boundary. |

**Why provisionally A3:** it preserves the actual evaluator's policy boundary, avoids divergent evidence copies, and gives global release and obligation retention explicit owners. This conclusion is conditional on implementing and testing the publication/lifecycle invariants, not a preference for more tables. If time cannot cover them, choose a frozen-context A1 investigation tool with **no global release export**, not an incomplete A3 that treats absence as clearance.

## 4. Safety invariants and candidate acceptance rules

The following are proposed requirements, **not claims about current functionality**. `E` means actual kernel `EXCLUDED_WITH_EVIDENCE` with `RELEASE_ELIGIBLE`; `A` means `AFFECTED`; `U` means `UNRESOLVED`. `PENDING`, `ERROR`, `STALE` and applicability `UNKNOWN` are orchestration states, never invented engine findings.

1. **All applicable active recalls must permit recall release.** A global release candidate requires a complete case-set generation and, for every active case, either auditable NOT_APPLICABLE evidence or APPLICABLE plus a current verified E result under its activated revision and required input horizon. No A/U/pending/error/stale/unknown case may be dropped from the conjunction. Store all contributors/blockers, not just the worst finding. This concerns recall clearance only; it is not shipment authorization.
2. **Unknown applicability is blocking.** No matching lot in an incomplete index is not proof of non-applicability. Prefer evaluating all registered motors against all active supported policies initially; kernel uncertainty stays U. If an applicability classifier is later added, it needs versioned positive scope evidence. An empty or unavailable active-case registry must not manufacture global RELEASE_ELIGIBLE: distinguish NO_ACTIVE_RECALL_RESTRICTION or NOT_EVALUATED.
3. **Replay original inputs and semantics.** Bind original policy bytes/digest, motor configuration/coverage, complete source vector, manifest, adapter/profile/canonicalization versions and engine artifact/profile. Replay cannot substitute “latest.” Verify semantic result separately from wrapper lifecycle/communication history and replay historical global composition under its original aggregation rule.
4. **Append revisions and decisions.** Revision activation, rollback and decision supersession are new immutable records. Historical records and displayed engine-local IDs remain unchanged; a later correction or withdrawal does not rewrite an old finding.
5. **Scope expansion invalidates prior clearance before publication.** Once an expansion is activated, affected/unknown candidate motors are PENDING/held until evaluated under the new revision. Old E is historical, not current clearance. Same event watermark with a new revision is a new evaluation context. A draft must not silently replace the activated revision, and a known risk warning should have a separate explicit hold path rather than being hidden as an unapproved edit.
6. **Corrections fan out to all potentially affected cases.** A change to a motor's evidence invalidates every active case for that motor in the first prototype, including cases previously considered out of scope. Preserve superseded and correction evidence. Policy/registry changes can invalidate the fleet. Event times alone cannot identify all dependencies.
7. **Withdrawal obligations survive later evaluations.** Append a withdrawal obligation linked to prior per-case and, where communicated, prior overall release. Keep communication UNKNOWN when unrecorded. Later holds, closure, a new policy or delivery retries cannot erase it. Delivery/acknowledgement are separate facts; avoid duplicate sends with explicit obligation/delivery keys. P2 demonstrates why projecting only the current decision is insufficient.
8. **Failure is not resolution.** Keep an old decision for history, mark the current case evaluation ERROR/STALE and block the global candidate. Successful cases retain their own actual results and never acquire a fabricated E or “resolved” label. Missing results are explicit blockers. A failed case cannot reduce the expected case count.
9. **Closure is an authorized lifecycle event, not an exposure verdict.** Require actor authority, reason, evidence, expected prior state/revision and effective time. Preserve all motor findings and outstanding obligations. Proposed conservative suspension remains blocking; reopening increments case-set generation and requires fresh evaluation before release. Whether an authorized closure removes a case's restriction is an explicit rule, not an E decision.
10. **Idempotency without losing audit evidence.** Same exact input identity and output reuses the same evaluation/decision. A new horizon creates an auditable evaluation receipt even when nonmaterial; material changes to policy/configuration, relevant evidence, findings, reasons, flags, attribution, review, obligations or global contributors create a new publication version. Do not reuse the current `_signature` as a complete materiality rule. Keep the full fresh raw kernel result, not old fields with only a new watermark. Canonical fingerprints need an explicit, versioned material-field specification; initially err toward recording potentially material changes.

### Publication and race condition study

A candidate publication token is `(caseSetGeneration, activatedRevisionMap, motorRegistryGeneration, motorEvidenceGeneration/vector, coverageContext, semantics, aggregationRuleVersion)`. Policy activation/capture/registration invalidates that token and marks the affected scope pending in the same durable transaction as the triggering change. A worker may compute outside a write lock, but must compare-and-publish only if its token is still current; otherwise retain the historical receipt and retry. No partially completed batch may be served as a current overall release.

An initial synchronous implementation can use short SQLite transactions to pin inputs, compute, then atomically publish guarded results and disposition. Holding a single write lock across all work is simpler but can block capture; benchmark it. WAL or an HTTP RLock alone does not establish case-set freshness. Long-lived UI release displays also need an explicit generation/as-of contract and invalidation mechanism; a future operational release action must recheck the token server-side. Exact realtime display behavior is an owner decision, not solved by hashing a response.

## 5. Proposed adversarial acceptance matrix — not executed

Assumptions: R1 is current-installation DE recall for lot L1; R2 may target NDE/L2 or historical damage as stated. Complete serial identity/coverage is present unless the row introduces uncertainty. `HOLD` below is proposed overall recall disposition, never a replacement for original per-case findings. An obligation is conditional if prior communication is unknown; confirmed communication requires actionable recipient tracking. An already outstanding obligation persists in **every** row.

| Scenario / stimulus | Expected per-recall results | Expected overall disposition | Notification/identity expectations |
| --- | --- | --- | --- |
| 1. One motor has affected L1 in DE and L2 in NDE | R1=A; R2=A under separate scoped policies | HOLD; both case/revision IDs visible | Ordinary case outreach requirements remain separate from withdrawal obligations; no prior-release withdrawal unless one existed. |
| 2. Clean R1 replacement, R2 still affected | R1=E; R2=A | HOLD; R1 clearance must not be labelled overall release | Preserve R2 obligations; clearing R1 cannot cancel them. |
| 3. Two recalls overlap the same lot | For identical current policies: A/A before repair, E/E after sufficient repair. If R2 historical, E for R1 and A pending inspection for R2 | HOLD until every applicable policy permits release | Distinct case/decision/obligation identities even when raw findings/evidence match; no duplicate semantic scope collapse. |
| 4. Expansion after shipment and a prior E | R1 old revision's E replays unchanged. New revision includes installed lot: PENDING then A. R2 stays independently current or is explicitly invalidated if its inputs changed | Immediately HOLD at expansion activation, before evaluation completes | Cross-revision withdrawal links old release; create conditional/required obligation based on its communication. Shipment is not evidence of clearance. |
| 5. Historical-damage policy added after replacement | R1 current-installation E remains E. R2 historical=A when trusted exposure exists and required inspection is missing; U when exposure is uncertain. Valid scoped PASS plus complete remediation can later give E | HOLD until R2 E or positively inapplicable; do not reuse replacement-only clearance | Prior overall release withdrawal is captured even though R2 has no previous per-case decision. | 6. | 8. Suspension, unauthorized closure, authorized closure, reopening | Suspension retains prior findings and blocks. Unauthorized closure rejected. | 9. Conflicting revisions share the same parent | Keep two immutable drafts; CAS activation accepts one or records explicit conflict. Conflicting/unresolved activation state is blocking, not last-write-wins | HOLD/PENDING until authorized resolution | No duplicate revision identity or decision IDs. If resolution expands a previously cleared scope, withdrawal rules apply. |
| 10. Partial evaluation failure | R1 actual E can remain visible as a case result; R2 ERROR with old result labelled historical/stale | HOLD with ERROR blocker; cannot report “all cases resolved” | Do not lose existing obligations; do not invent an affected finding or delivered notification just because evaluation failed. |
| 11. Replay after several policy/semantics revisions | Each old R1/R2 decision reproduces its own kernel fields under its stored policy/profile/configuration and vector. New revisions do not alter old results | Historical disposition replay uses historical case set; current view remains governed by current generation | Replay supersession/obligations from the original wrapper journal; wrong policy digest/profile/configuration/bytes must fail explicitly. |
| 12. Concurrent scope update and capture ingestion | Pause worker after pinning old inputs; commit policy/capture; let old worker finish. Its output cannot become current. Retry sees new revision and new vector, including references | HOLD/PENDING between invalidation and a matching complete publication | Exactly one publication for an exact input token; no lost obligations, source sequence duplication or half-published global clearance. Repeat with concurrent motor registration/closure. |
| 13. Repeated exact evaluation; changed explanation/evidence only | Exact input: same publication. Same finding but materially new cited evidence/flags/attribution/reasoning: new auditable decision; irrelevant metadata: new receipt as appropriate | Only complete fresh dispositions count; result label may remain unchanged | No lifecycle churn from an obligation added after comparison; one logical obligation survives later holds and retries. |
| 14. Empty/stale scope index, hidden sibling, or policy query failure | Applicability UNKNOWN/ERROR, not NOT_APPLICABLE; a filtered history cannot be accepted as the full engine case | HOLD/NOT_EVALUATED; never vacuous global release | Record missing scope evidence; no fabricated clearance or cancellation of prior obligations. |

Test construction should use actual v3 evaluation, separate synthetic truth, deterministic IDs/times and barriers controlling race schedules. Assert evidence/revision/coverage/vector provenance as well as findings. Report false releases and unnecessary holds separately. A test that merely asserts the same aggregator formula it implements is insufficient: include these independently authored safety scenarios, fault injection between writes/publication and historical byte-for-byte preservation checks.

## 6. Candidate data models and unchanged-kernel compatibility

These are logical candidates, not SQL migrations or an approved schema. Prefer opaque, stable case/motor identifiers and explicit foreign-key-like relationships; do not use engine-local display IDs as global primary keys.

| Candidate record | Identity and minimum research fields | Preservation / safety responsibility |
| --- | --- | --- |
| **RecallCase** | Stable case ID, external reference, immutable creation fact, owner/authority domain, lifecycle transition history, current lifecycle projection, activated revision reference, generation | Draft/active/suspended/closed states require explicit transition records; reopening refers to the prior case rather than overwriting it. |
| **RecallPolicyRevision** | Case ID + immutable revision ID/digest; human revision number unique within case; parent revision; exact policy bytes/canonical digest scheme; effective/activation times; author/approver; activation token; scope and inspection protocol IDs | Store draft and activation separately. No duplicate active child by accident; rollback is a new activation event. Coverage/configuration is referenced separately, not folded into the meaning of policy version. |
| **RecallDecision** | Global envelope ID scoped to case, revision, motor and publication sequence; raw kernel result; original engine-local ID if present; engine artifact/profile; policy/configuration/coverage digests; input/receipt reference; material fingerprint/version; prior standing envelope and transition cause | Raw engine output is immutable. Cross-revision supersession is wrapper metadata, never a rewrite of engine IDs or findings. Store full reasoning/evidence and distinguish failed attempts from decisions. |
| **MotorDisposition** | Motor ID + disposition version; aggregation rule version; case-set generation; revision map; input frontier; applicability proofs; contributing decision envelope IDs; pending/error/held blockers; prior disposition; computed/as-of time | Separate overall recall-clearance state from per-case engine findings. Immutable publications plus a guarded current projection; no overall release based on selected UI policy. |
| **EvaluationWatermark / Receipt** | Motor ID; full source vector including zeros; evidence manifest/hash; configuration/source-registry/session context; policy revision map or per-case revision; case/motor registry generation; adapter/canonicalization/semantics/artifact versions; accepted as-of boundary and result status | Preserve native producer occurrence/recordedAt, repository recordTime and local receipt separately in evidence. An exact retry key covers all safety inputs, not only max recorded time or engine watermark. |
| **NotificationObligation** | Stable obligation ID; case/motor and prior release reference (including overall release if relevant); triggering revision/evidence/lifecycle event; reason; authority; communication evidence UNKNOWN/confirmed; recipient/scope; append-only delivery/acknowledgement/resolution events; idempotency key | Durable journal independent of “current decision.” Delivery is never inferred from UI display. Resolution needs explicit rules/evidence; closure does not delete obligations. |

Applicability proofs, evaluation attempts, communication facts and lifecycle/activation events may need separate records rather than overloading these six entities. Exactly which should be tables versus typed immutable event records is unresolved.

### Can v3 remain unchanged?

**Yes, conditionally, as a one-motor/one-policy deterministic evaluation kernel.** It already supports the two exposure bases and versioned semantics replay. Proposed orchestration should feed the complete verified motor context into the existing `pramaan_recall.evaluate(..., Config.v3())`, preserve its raw output, and compose case/global publication metadata around it. Do not duplicate slot reconciliation, convert unknown into an empty baseline, or implement a second exposure evaluator.

**Not by treating existing `evaluate_series` as the whole new lifecycle.** Its local ID format, policy-hash-separated histories, limited signature and transition-only obligation fields do not satisfy cross-case/cross-revision requirements (P1/P2). A possible approach is an external append-only publication/obligation layer over fresh raw evaluations while leaving historical `Ledger.decide/replay` available for imported records. Whether to extend the ledger's interfaces or introduce a sibling orchestration layer needs owner approval. Preserve existing lifecycle results for historical replay; do not silently “repair” old records to new semantics.

Inspection reuse, future multi-part policies and changing coverage/trust contexts are compatibility gates. The kernel can remain unchanged only while the supported policy and evidence contract is respected; unsupported policy shapes must be rejected/held, not approximated by a union or implicit inspection sharing.

## 7. Migration and replay risks

Candidate **additive** migration, for approval only:

1. Quiesce the local writer for a verified consistent backup (use a SQLite-consistent backup procedure, not a live copy of only the database file while ignoring WAL). Hash and inventory original configurations, captures, events, policy bytes and decision runs; confirm integrity and rejection state before import. Rehearse rollback on a copy; no migration was run here.
2. Create new namespaced case/revision/envelope/journal records without UPDATE/DELETE to original tables or dropping triggers. Map the existing announcement to one legacy-import RecallCase. Empty databases remain explicitly unannounced. Multiple unexplained policy hashes or corrupt records are reconciliation blockers, not guesses about intended scope.
3. Preserve every original decision run, duplicate displayed ID, bundle digest and policy hash. Build a lookup key including legacy run ordinal/bundle position and policy digest; keep displayed IDs as scoped attributes. Do not rewrite `D-...-P1-v1`, recompute signed-like hashes or recalculate historical results under a newer profile to make keys unique.
4. Bind each old run to exact policy bytes. `decision_runs` does not itself store policy bytes, and normal Phase 3 announcements provide only the supported policy. If a digest cannot be matched to preserved policy bytes, label replay UNAVAILABLE/UNBOUND and block current reliance; do not reconstruct it from a displayed policy ID or current announcement. Archive coverage/configuration and engine artifacts/profile mappings needed for original replay.
5. Import obligation occurrences from **all** historical bundles, not just current notifications. Map legacy release references through their scoped context. Preserve unknown communication as UNKNOWN; old `NOT_SENT` projection is not evidence of delivery or of nobody receiving the decision. Link/supersede duplicate occurrences conservatively without erasing their provenance.
6. Before current multi-case operation, create a case-set generation and reevaluate all registered motors under each activated case. Imported E is historical until its required inputs/registry are current. Store new global dispositions rather than retroactively claiming that old single-policy decisions were globally safe. Test old replay paths and compare raw old table bytes/digests before/after.
7. Avoid prolonged dual writes without an explicit transaction/idempotency protocol. Candidate cutover: old reads/replay remain available, new orchestration becomes the only writer of new case/publication records, and the single-case API either selects an explicit compatibility case or rejects ambiguity. Never map an omitted case parameter to an arbitrary latest policy. Rollback may restore old read-only operation; it cannot present one-case clearance as multi-case global release.

Replay has three separate obligations: **kernel result reproduction**, **historical publication/supersession composition**, and **communication/notification history**. A single current-policy evaluation cannot reproduce all three. Preserve artifact versions in addition to semantics labels; changing the implementation behind a label can otherwise change old results. Historical snapshots also need durable integrity-checked archives; later database corruption can block the current ledger replay path even at an older vector.

## 8. Performance and selective reevaluation study

No new multi-recall load benchmark was run. Baseline measurements are synthetic, sequential, local Windows/Python 3.12/SQLite WAL results, **not capacity guarantees**:

- [Phase 3 application report](phase3-application-measurements.json): six motors, final 186 events, 20 growing-history replacements; capture through verified fleet decision median **1460.891 ms**, p95 **3061.802 ms**; selected-motor persisted evaluation median **572.902 ms**, p95 **1969.721 ms**. These include replay history growth and are not per-event/per-recall constants.
- [100-motor adapter benchmark](phase3-validation/performance.json): 800 events (8/motor), 300 samples; validated decision mean **7.9203 ms**, p95 **12.7287 ms**; cached-input engine mean **0.4622 ms**. This small-history benchmark is not representative of long-lived lifecycle streams.

Let M be motors, R active recall cases, E_m the motor's event count and H_mr retained evaluated horizons for a motor/case/revision. Full evaluation entails at least M×R predicate evaluations. With an approved shared immutable context, a useful conceptual cost is `sum_m(validation(E_m) + sum_r kernel(E_m, policy_r))`; without sharing it is approximately `sum_m sum_r(validation + kernel)`. These are cost decompositions, not measured complexity proofs. Sorting/reconciliation adds event-dependent cost; histories and evidence serialization matter.

Current `Ledger.decide` reconstructs every stored horizon and calls `snapshot()` for each, which validates stored motor rows before filtering, then evaluates the series. Work grows roughly with R×H×evidence processing rather than just R. Each appended run embeds all prior bundles/manifests. Cumulative stored payload work resembles `sum_over_runs_j sum_over_horizons_i<=j size(manifest_i)`; growing event histories can make this substantially worse than linear. A future context cache cannot simply bypass this verification without a reviewed integrity boundary.

**Illustrative small-history serial budget only**, using the measured mean 7.9203 ms per validated call and assuming one short-history call per pair, no shared validation benefit, no concurrency or UI/queue/capture overhead:

| Motors × active cases | Pair evaluations | Arithmetic estimate |
| --- | ---: | ---: |
| 100 × 1 | 100 | 0.79 s |
| 100 × 10 | 1,000 | 7.92 s |
| 1,000 × 10 | 10,000 | 79.2 s |
| 1,000 × 50 | 50,000 | 396 s |

These are extrapolations of a different dataset, not fleet measurements. The long-history Phase 3 times show why linear extrapolation can understate cost. Minimum future benchmark: M={10,100,1000}, R={1,2,10}, short/long histories and corrections, repeated policy revisions, cold/warm reads, writer contention and fault retries; measure capture-to-published/global-visible latency, queue lag, invalidation delay, replay cost, database growth and percentile tails. Record synthetic truth independently and test stale-publication rejection during load.

### Safe invalidation candidates

| Trigger | Conservative first-prototype invalidation | Conditions before selective narrowing |
| --- | --- | --- |
| Any accepted motor event, including correction/removal/inspection/untrusted observation/work order | All active cases for that motor | Sound dependency graph including superseded refs, sibling ambiguity, history, sessions and inspection protocols. A part/lot filter alone is insufficient. |
| Rejected input, integrity/configuration failure, source gap | All current reliance for that motor; explicit ERROR/hold | A resolved/reconciled failure policy, never ignoring a rejection to reuse E. |
| New/expanded/narrowed policy or exposure/inspection change | All registered motors for that case; revise global case-set generation | Complete scope census and auditable exclusion proofs; narrowing cannot erase history or old obligations. |
| New motor / recovered previously unknown genealogy | All active cases for that motor; update fleet completeness | Motor registry generation and complete applicability proof. |
| Case activation/suspension/closure/reopening | Global dispositions for affected census; reopening also case reevaluation | Authorized lifecycle evidence and precisely approved active-case/closure rules. |
| Coverage/trust/session/slot-label/semantics change | Every dependent case/motor context | Versioned configuration provenance and replay support; no in-place old coverage mutation. |
| Communication or obligation change | Notification and affected global/per-case publication context | Does not necessarily require rerunning exposure logic, but material obligation changes remain auditable and cannot disappear. |

A risk-increasing observation can change a formerly “unaffected” case; a historical policy can depend on a removed lot; an NDE sibling can affect DE attribution; a late correction can change old exposure; a changed source/session boundary can change completeness without changing a lot. Missing any of these creates missed-exposure risk. Start with full reevaluation and synchronous stale gates. Selective reevaluation is a later optimization to prove equivalent to full reevaluation over adversarial/metamorphic cases, not a prerequisite for the first prototype.

## 9. Smallest credible Phase 4 implementation boundary — proposal only

For a separate implementation authorization, propose one local SQLite database, two simultaneously active supported recall cases, immutable revisions with one authorized activation at a time, complete motor contexts, and unchanged v3 raw evaluation. No union-policy semantics, production distribution or selective cache. Demonstrate one current-installation policy and one supported historical policy with deliberately distinct protocol identity; expanding an activated scope and cross-revision withdrawal must be included, not deferred behind a “latest policy” shortcut.

Minimum proof points:

1. Additive case/revision/envelope/receipt/global-disposition/obligation records and scoped identity; historical Phase 3 bytes remain unchanged and replayable.
2. Full fleet × active-case evaluation with explicit pending/error/unknown states and atomic generation-checked publication. Persist independent case results and one overall recall disposition with complete contributors. Keep per-case E visible without implying overall clearance.
3. Case-scoped reads/commands, an explicit overall field and compatibility rejection when case selection is ambiguous. This is an API contract proof; unrelated UI redesign and production authorization systems are out of scope.
4. Durable obligation history across evidence and policy withdrawals, plus communication UNKNOWN. No external sending is required, but outstanding obligations must remain visible after subsequent evaluations.
5. Deterministic tests for the matrix, including activation/capture races and fault boundaries; existing v1/v2/v3/foundation/integration/UI behavior preserved where compatible, with intentionally changed contracts documented. No oracle or physical truth enters decision code.
6. Conservative lifecycle handling: reject unauthorized/unsupported transitions; support explicit authorized suspension/closure/reopening only after owner approves their semantics. If those rules are unresolved, the prototype must reject those commands and cannot claim complete lifecycle support.

A 36-hour demonstrator is an **estimate**, conditional on owner decisions and no baseline-audit blockers: roughly one workday for contracts/additive storage/migration rehearsal, one for orchestration and obligations, and the remainder for adversarial tests, race injection, replay verification and evidence reporting. This is tight for a single implementer; production identity, delivery, policy approval governance, long-history optimization and general multi-part rules are outside it. If the safety gates do not fit, reduce the claim to a frozen-snapshot investigation prototype rather than reducing the invariants.

### Recommendation and fallback

**Recommend A3 for an owner-approved prototype**, because the ledger is already shared and the kernel already evaluates independent policies. The new work is explicit case/revision identity, freshness/publication, applicability and durable lifecycle obligations. This is a direction for validation, not an approved schema or frozen architecture.

**Fallback A1:** independently evaluate two complete frozen contexts, archive each exact input, and publish only case-specific results plus an explicit pending/manual overall hold. If an overall aggregate is provided, it must still use a complete fixed case set and the same fail-closed invariants. Do not claim a live globally releasable platform without correction fan-out and currentness guarantees. **A2 union policy: NO-GO** for general evolution under the unchanged-kernel requirement; investigate only if the owner later requests a formally defined, separately verified combined-policy semantics.

### Owner decisions required before implementation

- Whether to proceed with A3 or the narrower A1 fallback, and whether Claude's independent audit changes the baseline/priority. P1/P2 should be reconciled with that audit; this report does not patch its subject.
- Define applicable population, positive NOT_APPLICABLE evidence, behavior when no active cases exist, and whether review flags or outstanding communication obligations independently block overall recall clearance beyond kernel action.
- Authorize case ownership/approval roles, activation/effective-time rules, conflicting-revision resolution, policy rollback, suspension/closure/reopening and emergency risk notices. Decide whether closure removes an operational restriction while retaining outstanding notifications.
- Approve the cross-revision/publication lifecycle boundary around an unchanged kernel, global envelope identity, materiality rules and fingerprint versioning; do not assume existing local decision IDs/signatures satisfy them.
- Decide whether/how an inspection may satisfy multiple cases/revisions and how protocol/qualification/scope provenance prevents accidental cross-credit. Resolve coverage/trust-configuration evolution separately from recall policy evolution.
- Define who receives per-case versus overall-release withdrawal notices, deduplication, communication evidence, delivery/acknowledgement/resolution, and retention when the original communication is unknown.
- Approve synchronous full reevaluation/publication barriers for the first prototype, acceptable capture blocking/latency, UI stale-display behavior, expected fleet/case/history size and the evidence required before selective invalidation.
- Approve additive migration/cutover/rollback and handling of unmatched policy hashes, rejection blocks, unavailable historical bytes and legacy ID collisions. No automatic repair or production migration is authorized by this research.

**Stop condition reached:** research report only. Architecture choice, lifecycle semantics and all implementation remain subject to explicit owner approval.
